# 0001 用 Rust 重写并采用共享核心结构

- 状态：接受
- 日期：2026-09-13
- 关联：[../design.md](../design.md)

## 背景

Python 版 Input Locker 把同一套业务规则（Caps×3 手势、密码缓冲、锁定生命周期）在 Windows、
X11、evdev、macOS 四个后端各写一份，配合共享标志、UI 回调和调度线程形成复杂生命周期。提交历史
显示同一个缺陷需要按平台各修一遍，漏一处就复现。

## 决策

1. 用 Rust 重写，目标三端一致行为，而不是把原类逐行翻译。
2. 结构固定为「共享核心 + 薄平台后端」：手势、密码、会话事件投影、协议读写在共享模块中只实现
   一份；平台模块只负责抓取/释放输入与系统资源，输入归一化为统一的物理键事件。
3. UI 只展示状态快照并发送命令，不参与解锁判定，也不直接释放输入。
4. 保留 aide 线协议字段与文件名，品牌更名不改协议。
5. 先做单 Cargo package，通过模块与 `cfg` 隔离；只有出现真实复用边界时才拆 crate。

## 后果

- 正面：平台差异收敛到明确边界；共享逻辑可脱离真实输入设备测试；类型化系统绑定与显式错误
  替代手写 FFI 与静默异常。
- 代价：Rust 不消除死锁、事件乱序与钩子失效等系统级风险，平台行为仍需逐端真机验证；macOS 与
  Windows 后端无法在 Linux 上编译前验证类型之外的运行时行为。
- 约束：不得因「Rust 已经统一」而省略真机验收；不得在共享核心内引入平台条件分支。
