# Stasis 设计方案

> Pause the machine. Rest the human.
>
> 状态：实现前设计基线。本文区分确定的产品行为和需要原型验证的技术选型；不代表已有实现。

## 1. 为什么重写

旧项目的主要风险不是 Python 行数，而是业务规则散落在 Windows、X11、evdev、macOS 后端，配合共享标
志、UI 回调和调度线程形成复杂的生命周期。

Rust 的价值是类型化系统绑定、显式错误和资源所有权；它不会自动防止死锁、事件乱序、系统钩子失效或
错误的业务状态迁移。不得把原有多个 Locker 类逐行翻译成多个 Rust 类。

本次目标：

1. Caps×3、密码、锁定生命周期、休息协议只实现一份。
2. UI 卡顿、失去焦点、隐藏时仍能用密码解锁。
3. 锁定成功、解锁完成、部分失败均有明确语义与日志。
4. 保持 aide 文件协议兼容，迁移不要求同时重写 aide。
5. 三端执行同一套行为用例，并分别做真实桌面验证。

非目标：操作系统登录锁、安全隔离、抵御本机管理员、拦截 Windows 安全注意序列、内核驱动、远程管理
服务。

## 2. 范围与跨平台契约

### 2.1 核心行为

| 项目 | 一致性要求 |
| --- | --- |
| 锁定 | 当前可访问的目标键盘、鼠标/触控设备抓取确认后才报告成功；部分抓取必须回滚 |
| 解锁入口 | 2 秒窗口内 3 次 CapsLock 实际按下；自动重复不计数 |
| 解锁模式 | sticky，只能开启，后续 Caps 不关闭、不清空已输入密码 |
| 密码 | 三端共用校验和缓冲逻辑；错误后关闭解锁模式，重新 Caps×3 |
| 密码解锁 | 可以立即提前结束休息，不设最短锁定时间 |
| 定时解锁 | UI 不参与判定；到期释放失败应重试并报错 |
| 状态 | 输入后端确认才改变实际状态，UI 不自行推断成功 |
| 系统恢复 | 释放本进程获取的资源，不把系统配置强行恢复为猜测的默认值 |
| 无权限 | 清楚说明缺失权限，不假报锁定成功 |

### 2.2 密码与键盘布局

第一版明确支持 ASCII 字母、数字，长度 1–64。配置加载、修改密码和底层输入三处遵守同一限制；不能允
许设置锁定后无法输入的密码。

拟采用统一物理 US-QWERTY 映射：平台原始键码转换为规范化物理键，字母大小写由左右 Shift 状态决定，
CapsLock 只承担解锁手势。顶部数字和数字小键盘均需有定义。UI 必须提示这一规则；非 US 布局用户看到
的键帽可能不匹配。

这是为可预测性作出的兼容限制，不宣称支持任意输入法/系统布局。若验收确认必须按当前布局输入，需先
确定三端布局解析方案，再放宽密码范围，不能各后端自行返回不一致的字符。

共享逻辑处理：按下/释放、重复过滤、左右 Shift 同时按住、设备移除后的修饰键清理、密码长度上限。
手势计数用单调时钟，不受系统时间校准影响。

macOS 上 `j` 与其它字母一样走普通 keyDown/keyUp，不需要修饰标志归一化；CapsLock 只被忽略，其
flagsChanged 语义不再影响解锁。

### 2.3 平台差异必须显式呈现

- Linux：拟统一使用 evdev，覆盖 X11 与 Wayland，要求目标输入设备访问权限。无权限时第一版明确拒绝
  锁定，**不静默回退系统锁屏**，因为系统密码解锁不是同一种行为。
- Windows：低级钩子不是安全隔离，Ctrl+Alt+Del 保留为系统出口。钩子超时可能被系统移除，Rust 无法
  消除这一限制。
- macOS：辅助功能权限、事件 tap 生命周期和系统保留操作仍受操作系统约束。
- Wayland：普通客户端不能保证强制前台、置顶或隐藏全局光标；这些不能成为解锁前提。

USB 存储禁用是单独的可选能力，不纳入第一阶段核心锁定。Windows/Linux 如实现，需记录原状态与恢复记
录；macOS 暂不承诺。托盘和隐藏光标也不阻塞核心交付。这些是相对旧程序的阶段性功能差异，不能标记为
完全等价替换。

### 2.4 Windows 后端实现记录（2026-09-20）

- **权限**：`WH_KEYBOARD_LL` / `WH_MOUSE_LL` 不需要管理员，可执行文件清单声明 `asInvoker`，
  不整程序提权。旧程序要求管理员不是沿用理由；USB 存储禁用若实现，另行申请权限。
- **权限边界（UIPI）**：低级钩子是用户态机制，受 UI 权限隔离约束。不提权运行时，发往更高完整性
  级别进程（以管理员运行的程序、任务管理器等）的输入**看不到也吞不掉**；UAC 的安全桌面同理
  （输入在另一个桌面）。因此不提权的锁定对这些窗口是**部分失效**，属权限边界而非实现缺陷。
  前台窗口完整性检测尚未实现，真机验证前不得声称「完整锁定」。
- **钩子失效**：Windows 对被静默移除的低级钩子不给任何通知（MSDN `LowLevelKeyboardProc`），
  无法直接确认「钩子已被移除」。实现改为检测可观测的前置条件：回调耗时超过阈值，以及钩子
  线程停止应答探测消息。前者上报 `Health`，后者上报 `Health` + `Released`，引擎据此释放
  锁定，不假装仍然锁着。
- **系统出口**：Ctrl+Alt+Del（SAS）由 winlogon 处理，低级钩子收不到，也不尝试拦截。
- **回调约束**：钩子回调只做 VK→规范化按键与 channel 发送，不写日志、不做磁盘 I/O；密码
  与逐键原始输入不进日志。

## 3. 项目结构

先用一个 Cargo package，通过模块隔离，不提前建立多个 workspace crate：

```text
src/
  main.rs              启动、日志、单实例、UI/引擎连接
  keypad.rs            共享解锁输入状态机
  session.rs           休息事件投影与调度规则
  protocol.rs          事件/command/ack 文件读写
  config.rs            配置、路径、密码验证
  engine.rs            唯一业务状态所有者
  ui.rs                eframe 展示与命令发送
  platform/
    mod.rs             最小后端边界与规范化输入事件
    linux.rs           evdev
    windows.rs         Windows 低级钩子
    macos.rs           CGEventTap
```

文件名是实施参考，不要求每个文件先建空壳。只有独立复用或依赖边界确实需要时再拆 crate。

## 4. 状态与线程模型

```text
OS 钩子 / 设备线程 ──规范化输入、Ready/Released/Lost──► 引擎线程
UI 主线程 ──────────Lock/ChangePassword/Exit────────► 引擎线程
文件轮询 ──────────休息请求、管理员命令────────────► 引擎线程
引擎线程 ──────────只读状态快照───────────────────► UI 主线程
```

引擎拥有锁状态、当前会话、密码输入状态和后端代次。平台线程仅持有必要的 OS 资源；UI 只发命令、显
示快照，不能直接释放抓取或修改生命周期标志。

业务状态至少区分 `Unlocked → Acquiring → Locked → Releasing → Unlocked`，失败带具体原因与残留资
源信息。不得用一个 bool 同时表示「希望锁住」「已经锁住」「线程活着」。每次抓取带 generation，忽
略旧代次的迟到事件。

关键约束：

- 钩子回调不得做 UI 调用、文件写入、日志刷盘或等待线程退出。
- 高频鼠标移动不进入业务队列；输入队列需有容量和溢出策略。事件丢失可能导致修饰键状态错误，不能静
  默忽略后继续声称正常。
- 解锁不在钩子线程内 join 自己；生命周期完成由资源所属线程报告。
- 不能只因线程存活就断言钩子仍有效。
- 后端初始化超时后仍可能迟到成功，必须取消并清理旧代次，再允许下一次抓取。
- 事件重放/文件 I/O 不得无界阻塞解锁处理；先限制输入规模和工作量，必要时把文件 I/O 移到独立
  worker，而非让钩子等待磁盘。

初始选用标准库线程、channel、超时等待；不为这一小型桌面工具引入 Tokio 或通用 actor 框架。

## 5. 资源与故障策略

采用显式 acquire/release，RAII 作为异常退出兜底。`Drop` 无法可靠报告恢复失败，也不会在断电、强制
终止或 abort 时保证执行，因此不能把它当作唯一恢复机制。

- 锁定中途失败：回滚已获得的键盘、鼠标、常亮资源，报告失败。
- 按键状态：测试锁前按住、锁中释放、解锁时仍按住、设备拔出。不能把 XTest 补发 release 当作
  Wayland 通用方案；uinput 有额外权限要求，需要真实设备原型决定处理方案。
- 热插拔：新设备需重新分类与抓取；抓取失败报告保护降级并按已定义策略退出/重试，不继续显示「完全
  锁定」。轮询存在短暂绕过窗口，不能承诺零窗口。
- 保持常亮：优先使用进程生命周期型 inhibitor/assertion，避免永久修改屏保设置。申请失败明确提示；
  若常亮是本次锁定的必要条件，则回滚输入抓取。
- 进程崩溃：输入句柄通常随进程退出释放，但不承诺恢复所有系统设置。禁止第一版为了 USB 禁用随意写
  永久系统策略。
- UI 关闭或崩溃：引擎应有明确退出信号并尝试释放；不能依赖 UI 析构顺序偶然完成。
- 单实例：同一协议目录只允许一个结果写入者。Stasis 内部用 OS 文件锁防多开；旧 Python 程序不遵守
  新锁，迁移时必须人工停用。

本产品优先避免把用户困在锁定状态；保留 OS 紧急出口，开发时始终准备独立的恢复通道。

## 6. aide 协议兼容

保留以下名字，品牌改名不改线协议：

```text
<协议目录>/
  input-locker-events/
    requests/*.json
    results/*.json
  input-locker-command.json
  input-locker-ack.json
  input-locker-last-command.json    aide 管理，Stasis 不改写
```

- schema：`input-locker.event/v1`。
- 字段：`eventId`、`sessionId`、`type`、`recordedAt`、`data`，可选 `causationId`。
- 请求：`rest.requested`，包含 `lockAt`、`unlockAt`；保留旧 `minUnlockSeconds` 读取兼容但不限制
  提前解锁。
- 结果：`rest.locked`、`rest.observed`、`rest.unlocked`、`rest.failed`、`rest.expired`。
- 会话用稳定 `sessionId` 关联；密码/command/到期解锁分别记录原因。
- 时间解析为 UTC，不能只按原始时间字符串排序；不同 UTC offset 必须正确排序。
- 先校验 schema、字段类型、时间范围、ID 和 data；坏文件隔离并限频记录，不中断整个目录消费。
- 文件读取设大小/数量防护，结果不可变；同目录唯一临时文件写完后原子发布，不使用跨文件系统 rename
  。

`rest-break/` crate 是本协议的调度侧实现：经 aide MCP 读会话、写 `rest.requested`，
不直接写事件目录；Stasis 本体（`src/session.rs`）是唯一消费者。

### 6.1 物理动作与日志不是一个事务

不能原样复制旧控制器后就宣称可靠：

1. 锁定成功但 `rest.locked` 写入失败：不能留下没有到期信息的无主锁。保留内存截止时间，并尝试回滚
   或进入明确的恢复状态。
2. 物理解锁成功但事件写入失败：必须保持解锁，重试记录；不能下一次重放看到旧 active 就立即重新锁
   人。需要持久化恢复/待发布记录，设计并测试崩溃窗口。
3. 已 active 的会话重启后按协议恢复；结束/过期会话不得重锁；同一物理锁只能有一个会话属主，重叠请
   求不能误解锁别人的锁。
4. 定时释放不能因写 observed 失败而被跳过；实际锁定区间与观测区间分开处理，不凭重启补算整段休息
   。

保留定期 observed（旧实现约 30 秒），但必须有历史归档/增量读取策略或明确规模上限；不让长期全量重
放拖慢密码解锁。

### 6.2 command/ack

继续支持 `{ "cmd": "lock" | "unlock", "id": "..." }`，ack 原样回传 id/cmd，结果为 ok/error，并包
含时间和错误信息。

认领后再执行，不能删除执行期间新来的命令。需要定义 `.processing` 崩溃恢复、重复 ID 和 ack 写入失
败行为；不承诺文件系统与 OS 动作的 exactly-once。优先采用幂等动作与可恢复的处理记录。

旧计划文件的 `_check_plan` 调度逻辑不移植。这里只兼容实际在用的事件流和 command/ack，而不是宣称
所有旧测试都应逐行移植。

## 7. 配置、日志与 UI

配置默认使用当前用户的应用配置目录，而不是可执行文件目录；显式 portable 模式可另行提供。Windows
Program Files、macOS app bundle 不应成为可写数据目录。

协议目录显式可配置，默认兼容 `~/Downloads`；事件目录覆盖优先级拟定为 `STASIS_EVENTS_DIR`、兼容
`INPUT_LOCKER_EVENTS_DIR`、配置/默认目录。错误配置不静默回退到另一个目录消费请求。

密码存储格式在实现配置前确定；最低要求：文件权限收紧、不写日志、不通过 UI 快照传递明文密码、保存
成功后才报告修改成功。首启需设置密码后才允许锁定，不沿用公开默认密码；旧配置导入显式操作并验证可
输入性。

日志记录代次、状态变化、sessionId、平台错误码和资源恢复结果，带滚动/保留限制。不得记录密码或逐键
原始输入。

UI 使用 Stasis 名字与完整标语，展示真实锁定状态、错误、解锁模式、密码长度和协议目录。默认不依赖
自动最小化/抢焦点完成流程。中文字体、键盘导航、对比度和未锁定时的密码修改可访问性纳入验收。

## 8. 技术选型（候选，不是验证结论）

| 层 | 候选 | 决策边界 |
| --- | --- | --- |
| UI | eframe/egui | 先做小面板；GPU/桌面依赖、字体和可访问性需验证；不承诺全静态零依赖 |
| Windows | windows / windows-sys 类型化绑定 | 钩子安装与消息循环同线程，unsafe 限制在平台边界 |
| Linux | evdev | 设备分类、权限、热插拔、按键释放是必须验证项 |
| macOS | core-graphics / objc2 系列 + Core Foundation | 根据 tap 和 run loop API 原型选择，不重复维护手写 FFI 声明 |
| 常亮 | keepawake | 逐平台核实 display/idle/sleep 权限和释放线程约束，不假定一个 crate 等于三端行为一致 |
| 协议 | serde/serde_json、chrono、uuid、tempfile | 保留兼容 JSON；核实 Windows 原子替换语义 |
| 日志 | tracing + 滚动文件 writer | 不在钩子回调同步写磁盘 |

不首选 rdev 的通用抓取封装：本项目需要可控的启动/停止、热插拔和故障语义，先评估其是否满足这些需
求再决定。此前对其维护状况及特定系统崩溃的讨论未经充分验证，不作为已确认事实。

Windows 不因旧程序要求管理员就默认让整个 GUI 提权；先验证输入钩子的最小权限需求，USB 等高权限功
能独立处理。macOS 打包/签名、Linux 动态库和桌面权限均属于交付工作，不是「编译成一个二进制」就自
动解决。
